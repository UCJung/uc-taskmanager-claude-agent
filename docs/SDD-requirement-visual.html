UC TeamSpace × UC TaskManager — v1.5.0 · 2026-03-22

🏗 시스템 개요
UC TeamSpace(팀 협업 플랫폼)와 UC TaskManager(Claude Code CLI 기반 자동 구현 파이프라인)가 Runner(scripts/runner.ts)를 통해 연결되는 3계층 통합 아키텍처다.
전체 시스템 연결 구조
uc-teamspace 프론트엔드 (React SPA)
HTTP REST + SSE
↓
uc-teamspace 백엔드 (NestJS)
pull-based polling 5초 간격
↓
Runner (scripts/runner.ts) — 상주 daemon
subprocess spawn
↓
Claude Code CLI (--output-format=stream-json)
HTTP callback
↓
uc-taskmanager WORK-PIPELINE 에이전트들
핵심 특징
🤖
멀티 에이전트 파이프라인
Router → Planner → Scheduler → Builder → Verifier → Committer. 6개 에이전트가 역할을 분담하여 요구사항을 자동 구현·검증·커밋한다.
⚡
3단계 실행 모드
direct(3 spawns) / pipeline(3 spawns) / full(2+2N spawns). Specifier+Planner 단일 spawn, Verifier+Committer 단일 spawn 결합으로 총 spawn 수 30% 감소.
🔒
3중 재시도 메커니즘
Verifier FAIL → Builder 재시도 / Committer FAIL → 체크포인트 재개 / Runner 비정상 종료 → PROGRESS.md 기반 복구.

⚡ 실행 모드 (execution-mode) v1.3 재설계
3종 실행 모드로 복잡도에 따라 파이프라인 깊이를 조절한다. 모든 경로에서 works/WORK-NN/ 구조 + PLAN.md + result.md + COMMITTER DONE 콜백이 보장된다.
direct
빌드/테스트 불필요 · 텍스트 수정 · 설정 변경
Builder (코드 수정) → Verifier+Committer (단일 spawn) (Specifier+Planner 생략)
spawn 수: 3개
pipeline
빌드/테스트 필요 · 단일 도메인 · sequential DAG

spawn 수: 3개
full
멀티도메인 / 복잡 DAG / 신규 모듈 / 5+ TASK
Specifier+Planner (단일 spawn) → Scheduler → [Builder → Verifier+Committer] × N (전체 파이프라인)
spawn 수: 2+2N개
판정 기준 외부화 (.agent/router_rule_config.json)
Router는 프로젝트 루트의 설정 파일에서 판정 기준을 읽는다. 파일이 없으면 내장 기본값을 사용한다.
direct build_test_required == false → 빌드 불필요 판정
pipeline single_domain + sequential DAG + max_tasks 이하
full full_conditions 중 하나라도 충족 (멀티도메인 / 5+ TASK 등)

🔄 WORK 파이프라인 상세 흐름
사용자 요청 → Router → (Planner) → (Scheduler) → Builder → Verifier → Committer 순서로 실행된다. 각 단계별 상세 흐름을 확인할 수 있다.
전체 흐름 요약
1. 사용자 요청 수신
"[기능추가] 새 기능 요청" — [] 태그 또는 자연어 요청
2. Router: execution-mode 판정
[] 태그 감지 → 파일시스템 스캔으로 WORK-NN 결정 → WORK-LIST.md IN_PROGRESS 추가 → direct/pipeline/full 판정 → .agent/router_rule_config.json 참조
3. Planner (full 모드만)
CLAUDE.md·README·package.json 탐색 → PLAN.md 작성 (Execution-Mode: full) → TASK-XX.md 생성 → TASK-XX_progress.md 템플릿 생성 → 사용자 승인 요청
4a. Builder dispatch
Serena MCP 우선 탐색 → 코드 구현 → 빌드/린트 자가검증 → progress.md STARTED→IN_PROGRESS→COMPLETED → <task-result> XML 반환
4b. Verifier+Committer dispatch (단일 spawn — v1.6)
[Verifier] Step 0: progress.md Gate 검사 → 7단계 검증 (빌드/린트/테스트/인수조건) → FAIL 시 Builder 재시도 (최대 3회) | [Committer] TASK-XX_result.md 생성 → PROGRESS.md 업데이트 → git add -A && git commit → 커밋 해시 백필 → TaskCallback 전송 → 다음 READY TASK 보고
5. 완료
모든 TASK 완료 → "WORK-NN 완료!" → 사용자가 "push 해줘" 요청 시 git push (Runner pollGitPush() 자동 처리)

⚙️ Runner (scripts/runner.ts) v1.1 대폭 보강
Runner는 상주 프로세스(daemon)로 동작하는 Bun 스크립트다. 백엔드 API를 5초 간격으로 폴링하여 대기 중인 실행을 수신하고, Claude Code CLI를 subprocess로 실행한 뒤 출력을 분석하여 백엔드에 실시간 피드백을 제공한다.

13.1 WORK ID 결정 (FILESYSTEM-FIRST)

›
파일시스템 스캔으로 현재 최대 WORK-NN을 읽고, WORK-LIST.md와 교차 검증하여 다음 ID를 결정한다. 두 소스가 불일치하면 더 큰 값을 사용한다.

13.3 멱등성 체크 버그 (수정 완료)

›
WorkTask 등록 시 findFirst 로직의 버그로 중복 등록되던 문제. v1.1에서 taskFile 기준 unique 체크로 수정 완료.

13.11 execution-mode 후방 호환 (v1.3)

›
dispatch에 execution-mode 속성이 없으면 full로 간주한다. PLAN.md에 Execution-Mode 필드가 없으면 full로 간주한다.

13.12 direct 모드의 검증 생략 위험 (v1.3)

›
direct 모드는 Verifier를 호출하지 않으므로 7단계 검증이 생략된다. Builder self-check(빌드+린트)만으로 완료 간주. 빌드가 없는 텍스트/설정 변경에만 사용해야 한다.

13.13 파일명 패턴 후방 호환 (v1.4)

›
Runner의 parseTaskFilename()은 구 형식(WORK-NN-TASK-XX-result.md)과 신 형식(TASK-XX_result.md) 모두 인식한다.

§3.13 ref-cache Reference File Caching

v1.5 신규

개요

<ref-cache>는 에이전트 파이프라인에서 참조 파일(shared-prompt-sections, xml-schema 등) 콘텐츠를 사전 로드하여 전달하는 선택적 XML 요소이다. 반복적인 디스크 읽기를 제거하여 파이프라인 효율을 높인다.

Phase 1 — 체인 전파 (Chain Propagation)

specifier (no ref-cache) → reads files → returns with <ref-cache>
  ↓ Main Claude copies <ref-cache>
planner → builder → verifier → committer → ...

Phase 2 — 선택 전달 (Selective Section Delivery)

Main Claude가 파이프라인 시작 시 참조 파일을 한 번 읽고, 에이전트별로 필요한 섹션만 추출하여 전달한다.
