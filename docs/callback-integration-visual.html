uc-taskmanager Callback Integration

Callback Integration 개요
uc-taskmanager 파이프라인은 외부 시스템과의 통합을 위한 선택적 HTTP 콜백을 지원한다. CLAUDE.md에 URL 설정이 있는 경우에만 활성화되며, 설정이 없으면 파이프라인은 standalone 모드로 동작한다.
01
Optional Activation
TaskCallback / ProgressCallback URL이 설정된 경우에만 활성화. 미설정 시 파이프라인에 영향 없음.
02
Failure Tolerance
curl 실패 시 경고만 출력하고 계속 진행. 콜백 실패가 TASK 실행을 절대 블록하지 않음.
03
Universal Compatibility
콜백 미설정 프로젝트는 기존과 동일하게 동작. 하위 호환성 완전 보장.
04
Mode-Invariant
direct / pipeline / full — 모든 execution-mode에서 COMMITTER DONE TaskCallback 전송 불변 보장.

CLAUDE.md 설정
프로젝트의 CLAUDE.md에 다음 세 필드를 추가하여 콜백을 활성화한다. 세 필드 모두 선택 사항이다.
설정 예시
## Task Callbacks TaskCallback: http://your-system.com/api/v1/task-result ProgressCallback: http://your-system.com/api/v1/task-progress CallbackToken: sk_live_your_bearer_token
설정 필드 상세
FieldRequiredDescriptionExample
TaskCallback Optional TASK 완료 결과를 수신할 HTTP 엔드포인트 (POST) http://localhost:3000/api/v1/task-result
ProgressCallback Optional 진행 상황 업데이트를 수신할 HTTP 엔드포인트 (POST) http://localhost:3000/api/v1/task-progress
CallbackToken Optional Authorization 헤더용 Bearer 토큰 sk_test_abcd1234...
미설정 시 동작
TaskCallback 미설정

ProgressCallback 미설정
진행 상황 업데이트 전송 없음
CallbackToken 미설정
Authorization 헤더 없이 curl 요청

uc-teamspace 통합 예시
## Task Callbacks TaskCallback: http://localhost:3000/api/v1/execution/{{executionId}}/task-result ProgressCallback: http://localhost:3000/api/v1/execution/{{executionId}}/task-progress CallbackToken: sk_live_execution_token_xyz
Callback 실행 흐름
execution-mode에 따라 콜백 전송 주체가 달라진다. 모드를 선택하여 시퀀스를 확인한다.
direct 모드 — Specifier 겸임 수행
빌드/테스트 검증 불필요한 단순 작업. Specifier가 builder/committer 역할을 겸임하여 콜백을 직접 전송한다.
pipeline / full 모드 — 서브에이전트 수행
Builder가 ProgressCallback을, Committer가 TaskCallback을 전송한다. v1.6.0부터 Verifier와 Committer는 단일 spawn으로 결합 실행된다. pipeline에서 Dispatcher는 Main Claude(Specifier+Planner spawn 완료 후), full에서는 Scheduler.
Phase별 타임라인 v1.6: Verifier+Committer 단일 spawn 결합
Builder
(spawn 1)
파일 수정 후 progress.md 갱신 → ProgressCallback 설정 시 curl POST → 실패 시 WARNING 출력 후 계속 → task-result 반환
Verifier+
Committer
(spawn 2)
[Verifier] Builder 결과 검증 → Acceptance Criteria 확인 → 콜백 없음
[Committer] (동일 spawn — verifier 완료 후) result.md 생성 → git commit → TaskCallback 설정 시 curl POST → 실패 시 WARNING 후 계속 → task-result + commitHash 반환
Payload Schema
콜백 요청의 JSON 페이로드 구조와 HTTP 요청 형식을 설명한다.
TaskCallback Payload
git commit 완료 후 1회 전송. Committer(또는 direct 모드에서 Specifier)가 전송.
{ "workId": "WORK-09", "taskId": "TASK-01", "status": "SUCCESS" // SUCCESS | PARTIAL | FAILED, "what": "committer.md에 TaskCallback 섹션 추가 및 curl 조건부 호출 구현", "why": "외부 시스템이 TASK 완료 알림을 수신할 수 있도록 설계", "caution": "curl 실패 시 commit 완료를 블록하지 않아야 함", "incomplete": "", "filesChanged": ["agents/committer.md"], "commitHash": "a3dc4f0", "timestamp": "2026-03-12T10:15:30Z" }
FieldTypeDescription
workIdstringWORK 식별자 (예: WORK-09)
taskIdstringTASK 식별자 — WORK 프리픽스 미포함 (예: TASK-01)
statusenumSUCCESS = 전체 완료 / PARTIAL = 일부 미완 / FAILED = 실패
whatstring변경 내용 요약 (파일 생성/수정, 신규 기능, 2-5줄)
whystring구현 이유, 대안 검토 (2-4줄)
cautionstring엣지 케이스, 조건부 완료, 주의사항 (1-3줄)
incompletestring미완료 항목 (완료 시 빈 문자열)
filesChangedarray변경된 파일 경로 목록
commitHashstringGit commit hash (단축형, 예: a3dc4f0)
timestampstringISO 8601 UTC 타임스탬프
ProgressCallback Payload
progress.md 체크포인트 갱신 후 전송. Builder(또는 direct 모드에서 Specifier)가 TASK당 여러 번 전송.
{ "workId": "WORK-09", "taskId": "WORK-09-TASK-02", "status": "IN_PROGRESS" // IN_PROGRESS | COMPLETED | FAILED, "checklist": [ { "item": "agents/builder.md 수정", "done": true }, { "item": "agents/shared-prompt-sections.md 확인", "done": true }, { "item": "문서 업데이트", "done": false } ], "currentReasoning": "builder.md 변경 완료. shared-prompt-sections.md 남은 작업 진행 중.", "timestamp": "2026-03-12T10:16:45Z" }
FieldTypeDescription
workIdstringWORK 식별자
taskIdstringTASK 식별자
statusenumIN_PROGRESS = 진행 중 / COMPLETED = 완료 / FAILED = 실패
checklistarray완료/미완료 작업 목록 (item 이름 + done boolean)
currentReasoningstring현재 진행 상황 및 남은 작업 요약
timestampstringISO 8601 UTC 타임스탬프
다중 전송: TASK당 N회 전송됨. 파일 1 완료 → callback, 파일 2 완료 → callback, 최종 상태 → callback 순서로 발생한다.
HTTP 요청 형식
TaskCallback Request
curl -X POST "$TASK_CALLBACK" \ -H "Content-Type: application/json" \ -H "X-Runner-Api-Key: $TOKEN" \ -d '{"workId":"...","status":"SUCCESS",...}'
ProgressCallback Request
curl -X POST "$PROGRESS_CB" \ -H "Content-Type: application/json" \ -H "Authorization: Bearer $TOKEN" \ -d '{"status":"IN_PROGRESS","checklist":[...]}'
예상 응답
2xx — 콜백 수신 완료
4xx/5xx — 처리 실패 → WARNING 출력 후 계속
Network Error — 연결 실패 → WARNING 출력 후 계속
에러 처리 전략
콜백은 best-effort 알림이다. 외부 시스템의 가용성에 파이프라인 신뢰성이 의존하지 않도록 설계되었다.
!
curl 연결 실패
시나리오: curl: (7) Failed to connect or curl: (28) Operation timeout
동작: 경고 메시지 출력 후 TASK 실행 계속 진행. 재시도 없음. Commit/result 이미 완료된 상태.
curl ... 2>/dev/null || echo "WARNING: callback failed, continuing..."
401
인증 실패 (401/403)
시나리오: 외부 시스템이 401 Unauthorized 또는 403 Forbidden 반환
동작: 경고 출력 후 계속. CLAUDE.md의 CallbackToken 값 확인 필요.
1. CallbackToken 값 검증 → 2. 엔드포인트 인증 요구사항 확인 → 3. curl 수동 테스트
30s
타임아웃
기본값: curl 기본 타임아웃 (약 30초) 사용
수신 측 권장: 느린 처리로 발신자를 블록하지 말 것. 멱등성 구현 권장.
수신 측: 즉시 200 반환 → 비동기 처리 패턴 권장
설계 근거
파이프라인 우선 원칙
외부 시스템 가용성과 파이프라인 신뢰성을 분리. 네트워크 일시 장애는 비치명적으로 처리.
Best-Effort 알림
콜백은 편의 기능. 필요하면 외부 시스템이 클라이언트 폴링으로 보완 가능.
멱등성(Idempotency) 설계
TaskCallback
멱등 키: commitHash
동일 commitHash → 중복 (무시)
TASK당 1회만 전송
ProgressCallback
멱등 키: (taskId, timestamp)
동일 timestamp → 같은 체크포인트 중복
다른 timestamp → 새로운 체크포인트
외부 시스템 구현 가이드
TaskCallback과 ProgressCallback을 수신하는 외부 시스템 구현 방법을 설명한다.
구현 체크리스트
  • ✓엔드포인트가 Content-Type: application/json POST 요청을 수신
  • ✓Authorization: Bearer <token> 또는 X-Runner-Api-Key 헤더 검증
  • ✓JSON 페이로드를 스키마에 따라 파싱
  • ✓TASK 결과를 DB 또는 캐시에 저장
  • ✓200 OK (또는 204 No Content) 즉시 반환
  • ✓실패한 요청에 대한 에러 로깅 구현
  • ✓중복 콜백에 대한 멱등성 구현
  • ✓(선택) status 기반 알림 트리거 (SUCCESS, FAILED 등)
  • ✓(선택) 진행 상황 실시간 대시보드 업데이트
Node.js 핸들러 예시
// POST /api/v1/execution/:executionId/task-result app.post("/api/v1/execution/:executionId/task-result", (req, res) => { const { workId, taskId, status, commitHash, timestamp } = req.body; // 멱등성: commitHash 중복 체크 if (db.existsByCommitHash(commitHash)) { return res.status(200).json({ received: true, duplicate: true }); } db.updateTaskResult({ executionId: req.params.executionId, taskId, status, commitHash }); if (status === "SUCCESS") { notifications.send({ type: "task_completed", taskId }); } res.status(200).json({ received: true }); }); // POST /api/v1/execution/:executionId/task-progress app.post("/api/v1/execution/:executionId/task-progress", (req, res) => { const { taskId, status, checklist, timestamp } = req.body; const done = checklist.filter(c => c.done).length; realtime.emit("task_progress", { executionId: req.params.executionId, taskId, status, progress: `${done}/${checklist.length}`, timestamp }); res.status(200).json({ received: true }); });
로컬 테스트 방법
1. 로컬 수신기 시작
# netcat으로 간단히 수신 nc -l 127.0.0.1 3000
2. CLAUDE.md에 추가
TaskCallback: http://127.0.0.1:3000/task-result ProgressCallback: http://127.0.0.1:3000/task-progress CallbackToken: test_token_123
3. curl 수동 테스트
curl -X POST "http://127.0.0.1:3000/task-result" \ -H "Content-Type: application/json" \ -H "Authorization: Bearer test_token_123" \ -d '{"workId":"WORK-09","taskId":"TASK-01","status":"SUCCESS","commitHash":"abc123"}'
