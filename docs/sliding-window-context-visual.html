Solution: Sliding Window Context Transfer

Transfer reasoning context (why, caution, incomplete) between agents using a sliding window. Recent context is detailed; older context is compressed or dropped.

3 Design Principles

The Sliding Window Context Transfer system is built on three core principles.

01

Sliding Window

Recent agent info is detailed, older info is compressed or dropped.

DistanceDetail LevelContent
1 step backFULLwhat + why + caution + incomplete
2 steps backSUMMARYwhat only (1-3 lines)
3+ steps backDROPNot transferred
02

Only Needed Context

Each agent only needs context for the work it inherits.

Verifier needs to know why Builder implemented it that way.
Verifier does not need to know why Planner created that TASK.
03

Separation of Concerns

result.md writing responsibility moved from Builder to Committer.

Builder: Focus on implementation only. Record checkpoints in progress.md.
Committer: Synthesize builder + verifier context-handoff into result.md.

context-handoff Structure

The core data structure for transferring reasoning between agents.

XML Structure
<context-handoff from="{agent}" detail-level="FULL|SUMMARY|DROP"> <what>What was changed/verified</what> <why>Why this approach was chosen</why> <!-- FULL only --> <caution>What to be careful about</caution> <!-- FULL only --> <incomplete>Unfinished items</incomplete> <!-- FULL only --> </context-handoff>
Field Guide
FieldLengthContent
what2-5 lines (FULL), 1-2 lines (SUMMARY)File names, function names, change summary
why2-4 linesTechnical rationale, alternatives considered, constraints
caution1-3 linesLinked code, side effects, manual verification needed
incomplete1-2 linesUnfinished items, what next agent should handle

Execution Mode Context Flow

The sliding window operates in pipeline and full modes. Direct mode has no context transfer issue.

Direct Mode - Single Session

Router handles everything in a single session. No sub-agent handoff needed. Context accumulates naturally.

Router: Analyze
Read specs, understand requirement
↓
Router: Implement
Write/modify code (same session, context preserved)
↓
Router: Self-Check
Build + lint verification
↓
Router: result.md + Commit
Generate result report, git commit, callback
No context transfer overhead
Pipeline Mode - Builder → Verifier+Committer (단일 spawn — v1.6)

Full Mode - Cross-TASK Context Transfer

When TASK-N completes and TASK-N+1 starts, the new builder gets a fresh session. Scheduler automatically includes context-handoff from preceding TASKs based on sliding window rules. Verifier+Committer는 각 TASK마다 단일 spawn으로 결합 실행된다.

TASK-N Pipeline
Builder → Verifier+Committer (단일 spawn) → result.md created
↓ result context-handoff
Scheduler
Reads result.md, applies sliding window, embeds context in dispatch XML
↓ FULL / SUMMARY / DROP
TASK-N+1 Builder
New session. Receives context from previous TASKs via scheduler dispatch.

Crash Recovery

If builder crashes mid-work, on re-dispatch it reads progress.md and resumes from the last checkpoint.

Builder Crash
Session terminated. progress.md shows IN_PROGRESS with partial file list.
↓
Re-dispatch
Scheduler detects incomplete TASK, dispatches builder again.
↓
Resume
Builder reads progress.md, skips completed files, continues from checkpoint.

Scaling Behavior
Traditional

Each TASK accumulates all previous results. Context grows linearly with TASK count. At TASK-10, the context contains all 10 previous results.

O(N) context growth
Sliding Window

Always carries only 2 previous contexts (FULL + SUMMARY). Context stays constant regardless of TASK count. At TASK-10, same context size as TASK-03.

O(1) constant context
Direct Mode Bonus

In direct mode, sub-agent session initialization cost (~12,500 tokens per agent) is completely eliminated. Router handles everything in a single session with zero context transfer overhead.

+12,500 tokens saved per TASK (session init cost = 0)
